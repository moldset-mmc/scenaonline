# Установка SCENA: зафиксированный пилот MBStudio

Состояние архитектуры проверено по коду `6c1402ec0ccef9709ed67fd4e20f6d4fd8bd5c5c`, 16.09.2026. Это инструкция эксплуатации существующего пилота и основа будущего установщика. Для нового владельца сначала выполнить условия [REPLICATION.md](docs/REPLICATION.md).

## Состав установки

| Слой | Реализация | Что сохраняется |
| --- | --- | --- |
| Исходники | GitHub `moldset-mmc/scenaonline` | Код, зависимости, документация, разрешённые стартовые медиа |
| Веб-сервер | Vercel Container, Python 3.12, Tornado | Отдаёт HTML и обрабатывает запросы |
| База | Turso через `scena_database.py` | Настройки, услуги, график, заявки, заказы, PRO, служебное состояние |
| Private Blob | `scena_media.py`, `scena_web/storage.py` | Оригиналы и приватные служебные файлы |
| Public Blob | Публикация разрешённых изображений | Публичные версии изображений |
| DNS / HTTPS | Основной адрес `mbstudio.scena.life` | Доменная привязка и сертификат |
| Поиск и аналитика | Настройки профиля + внешние кабинеты | Canonical, карта, языки, подтверждения и счётчик |

Облачный диск `/tmp` используется как временная рабочая область. Значение `SCENA_DB_PATH=/tmp/scena-cloud/scena_master.db` не означает, что рабочая облачная база хранится только в этом файле: при `SCENA_CLOUD=1` адаптер подключается к Turso.

## Реальный путь сборки и запуска

1. `Dockerfile.vercel`: образ `python:3.12-slim`, установка `requirements-web.txt`.
2. `deploy/build_web_assets.py`: создание хешированных публичных файлов и манифеста из разрешённых исходников.
3. `python deploy/start_web.py`: проверка обязательной конфигурации через `scena_web.runtime_config.configure`, установка `SCENA_NATIVE_WEB=1`.
4. `scena_web/domain_redirect.py`: создание приложения и ограниченных редиректов старых публичных хостов.
5. `scena_web/bootstrap.py`: инициализация схемы, ключа сессий, версии пароля, проверок хранилищ и одноразовых миграций.
6. Tornado слушает `PORT` (по умолчанию 80), отдаёт готовый HTML; формы и временное состояние доступны между экземплярами через общее хранилище.

Прежний облачный Streamlit launcher, WebSocket-прокси и временный Streamlit preview удалены из текущего дерева после перехода на native HTML; их история остаётся в Git. Production использует только `requirements-web.txt`. Локальный Streamlit запускается отдельно через `start_scena.py` и `requirements.txt`.

## Обязательные переменные сервера

Имена подтверждены функцией `configure` в [`scena_web/runtime_config.py`](scena_web/runtime_config.py). Значения вводятся в защищённые настройки окружения, а не в Git, командные примеры или Dockerfile.

| Имя | Назначение |
| --- | --- |
| `SCENA_TURSO_TURSO_DATABASE_URL` | Адрес индивидуальной базы |
| `SCENA_TURSO_TURSO_AUTH_TOKEN` | Серверный доступ к этой базе |
| `SCENA_PUBLIC_BLOB_READ_WRITE_TOKEN` | Доступ к публичному хранилищу |
| `SCENA_PRIVATE_BLOB_READ_WRITE_TOKEN` | Доступ к приватному хранилищу |
| `SCENA_ADMIN_PASSWORD` | Пароль кабинета; код требует минимум восемь символов |

Платформа также передаёт `VERCEL`, `VERCEL_ENV`, `VERCEL_GIT_COMMIT_SHA`, `VERCEL_DEPLOYMENT_ID`/`VERCEL_URL` и порт. Ключ сессий создаётся и хранится сервером; его нельзя копировать между независимыми клиентами. Не передавать секреты production в изолированный preview или публичный экспорт.

При тестировании `SCENA_WEB_TESTING=1` обходит облачную конфигурацию и требует тестовую базу и пароль. Это режим проверки, не способ установки рабочего сайта.

## Как был доведён пилот

1. Существующий GitHub-репозиторий подключён к существующему Vercel-проекту `scenaonline`.
2. Созданы Turso и два Blob-хранилища; подключены серверные переменные и пароль кабинета. Историческая квитанция: [HOSTING-PROPOSAL.md](deploy/HOSTING-PROPOSAL.md).
3. Реализованы постоянные адаптеры данных, приватность оригиналов, резервные копии и серверный вход.
4. Облачный Streamlit заменён на native HTML/Tornado; добавлены мобильные редакторы, частичные обновления, локальное переключение календаря и сохранённые публичные страницы.
5. Настроены Telegram-лиды магазина и услуг, действия со статусами, медиатека и настраиваемые QR. Реальная доставка в конкретного бота требует отдельного доказательства.
6. Основным адресом окончательно выбран `mbstudio.scena.life`; публичные старые адреса перенаправлены на него. Реализованы ЧПУ RU/RO/EN, метаданные, пустые разделы noindex, карта сайта и аналитика.
7. Google обработал sitemap, Яндекс подтвердил права и принял карту в очередь. Даты и пределы проверки: [чекпойнт](docs/MBSTUDIO-CHECKPOINT.md).

Это история выполненного внедрения, а не перечень действий, которые нужно повторить на действующем MBStudio.

## Доменные миграции и индивидуальные настройки

Канонический адрес хранится в `profile_settings.public_base_url`. Настройки SEO редактируются через кабинет и используются `scena_seo.py`. В пилоте `mbstudio_migration.py` атомарно записала основной адрес, SEO-флаги, счётчик и Yandex verification, сохранив прежние значения в квитанции.

Маркеры `seo_origin_migration:scena.life:v1` и `seo_origin_migration:mbstudio.scena.life:v1` предотвращают повторное применение. Не удалять их для «повторной установки». Поздние правки владельца должны сохраняться.

Для нового клиента нельзя просто запустить эти пилотные миграции. Нужны собственные домен, контент, счётчик и подтверждения; точные привязки перечислены в [REPLICATION.md](docs/REPLICATION.md).

## Обновление существующей установки

1. Прочитать текущий чекпойнт; сверить GitHub SHA, deployment и фактический основной адрес.
2. Подготовить и проверить изменения на изолированных данных. Использовать проверки именно затронутого поведения; не считать старые тесты приёмкой новой версии.
3. При изменении схемы или данных иметь актуальную приватную резервную копию и понятный откат. Описать изменения и согласовать внешнюю публикацию по действующим правилам владельца.
4. Опубликовать разрешённую версию в существующий проект. `main` подключена к production; изменение этой ветки может запустить деплой.
5. Проверить deployment ID/READY, `/healthz`, вход и сохранение в кабинете, изображения и затронутые формы. Проверить данные после нового запуска. Синтетические заявки использовать на тестовом стенде; не рассылать сообщения реальным клиентам для проверки.
6. Сохранить квитанцию: SHA, deployment, дата, выполненные проверки и оставшиеся ограничения.

Документальные checkpoint-ветки можно исключать из автоматического развёртывания точным правилом `git.deploymentEnabled` в `vercel.json`. Это не отключает обычные обновления `main`. [Документация Vercel](https://vercel.com/docs/project-configuration/git-configuration).

## Восстановление

GitHub сохраняет программу и правила установки; актуальные данные владельца находятся в Turso/Blob. Данные и изображения экспортируются приватно через кабинет. Инструкции: [LOCAL-GUIDE.md](LOCAL-GUIDE.md), код облачного восстановления — [`scena_cloud_restore.py`](scena_cloud_restore.py).

Сначала проверить восстановление в отдельном окружении. Откат версии кода не равен откату базы. Возвращать старую базу поверх новых заявок и правок владельца нельзя. Для отката SEO-миграции читать её квитанцию и возвращать только значения, которые не были затем изменены владельцем.

Полное восстановление нынешнего production в новую облачную установку этим документальным проходом не проводилось. Не выдавать этот документ за новый проверенный disaster-recovery-тест.
